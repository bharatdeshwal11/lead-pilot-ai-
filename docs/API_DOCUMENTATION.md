# API documentation

The API uses JSON and same-origin session authentication. OpenAPI is generated by springdoc. In the local Compose stack, open the [Swagger UI](http://localhost:3000/swagger-ui/index.html) or fetch the [OpenAPI JSON](http://localhost:3000/v3/api-docs). Run the stack before opening these addresses.

## Authentication and users

| Method and path | Purpose |
| --- | --- |
| `GET /api/auth/csrf` | Get the CSRF token and the header name to use for mutations. |
| `POST /api/auth/login` | Authenticate with `email` and `password`. |
| `GET /api/auth/me` | Return the session user's `id`, `name`, `email`, `role` and `active`. |
| `POST /api/auth/logout` | Invalidate the session. Returns `204`. |
| `GET /api/users` | List accounts. Administrator only. |
| `POST /api/users` | Create an account from `name`, `email`, `role` and `password`. Administrator only. |
| `PATCH /api/users/{id}` | Update the supplied account fields. Administrator only. |
| `GET /api/users/assignees` | Return eligible active sales agents as `{id, name}`. A sales agent sees their own assignment option. |

Keep the session cookie in your client and send the current CSRF token on each state-changing request. After login and logout, fetch the token again before sending another mutation.

```bash
base=http://localhost:3000
jar=$(mktemp)
csrf=$(curl -fsS -c "$jar" -b "$jar" "$base/api/auth/csrf")
header=$(jq -r '.headerName' <<<"$csrf")
token=$(jq -r '.token' <<<"$csrf")

read -r -p "Demo email: " demo_email
read -r -s -p "Demo password: " demo_password
printf '\n'
jq -n --arg email "$demo_email" --arg password "$demo_password" '{email:$email,password:$password}' |
  curl -fsS -c "$jar" -b "$jar" -H "$header: $token" \
    -H 'Content-Type: application/json' -d @- "$base/api/auth/login"
unset demo_password

csrf=$(curl -fsS -c "$jar" -b "$jar" "$base/api/auth/csrf")
header=$(jq -r '.headerName' <<<"$csrf")
token=$(jq -r '.token' <<<"$csrf")
curl -fsS -b "$jar" "$base/api/auth/me"
```

## Leads

| Method and path | Purpose |
| --- | --- |
| `GET /api/leads` | List visible leads with search, filtering, sorting and pagination. |
| `POST /api/leads` | Create a lead. An agent-created lead is assigned to that agent. |
| `GET /api/leads/{id}` | Fetch a lead in the current user's scope. |
| `PATCH /api/leads/{id}` | Update supplied fields. Administrators can change assignment. |
| `DELETE /api/leads/{id}` | Delete a lead. Administrator only. |
| `GET /api/leads/{id}/activities` | List dated lead changes in the current user's scope. |

`GET /api/leads?q=site%20visit&status=NEW&priority=HIGH&source=WEBSITE&page=0&size=20&sort=createdAt,desc` combines filters. `assignedUserId` is also supported. Allowed sort fields are `createdAt`, `updatedAt`, `customerName`, `email`, `source`, `status` and `priority`. The envelope contains `content`, `totalElements`, `totalPages`, `page` and `size`.

Example body for `POST /api/leads`:

```json
{
  "customerName": "Isha Mehra",
  "email": "isha.mehra@example.test",
  "phone": "+91 90000 01014",
  "enquiryMessage": "I'm looking for a 3BHK apartment in Greater Noida. My budget is 90 lakh and I need to move within two months. Can we arrange a site visit?",
  "source": "WEBSITE"
}
```

Example response with representative IDs and timestamps:

```json
{
  "id": 41,
  "customerName": "Isha Mehra",
  "email": "isha.mehra@example.test",
  "phone": "+91 90000 01014",
  "enquiryMessage": "I'm looking for a 3BHK apartment in Greater Noida. My budget is 90 lakh and I need to move within two months. Can we arrange a site visit?",
  "source": "WEBSITE",
  "status": "NEW",
  "priority": "MEDIUM",
  "assignedUser": null,
  "createdAt": "2026-11-18T10:00:00Z",
  "updatedAt": "2026-11-18T10:00:00Z"
}
```

Lead status values are `NEW`, `CONTACTED`, `QUALIFIED`, `WON` and `LOST`. Sources are `WEBSITE`, `EMAIL`, `MANUAL` and `OTHER`. Priorities are `HIGH`, `MEDIUM` and `LOW`. A PATCH can send `{"status":"QUALIFIED"}` to change status. It can send `{"phone":null}` to clear a phone or `{"assignedUserId":null}` to clear an assignment, subject to authorization.

## AI analyses and drafts

| Method and path | Purpose |
| --- | --- |
| `POST /api/leads/{id}/analyze` | Analyze the saved enquiry and persist a new analysis. |
| `GET /api/leads/{id}/analyses` | Fetch the lead's analysis history. |
| `POST /api/leads/{id}/reply-draft` | Generate and save a new reply draft. |
| `GET /api/leads/{id}/reply-drafts` | Fetch the lead's draft history. |
| `PATCH /api/reply-drafts/{id}` | Edit a draft or submit it for review. |
| `POST /api/reply-drafts/{id}/approve` | Approve a draft awaiting review. Administrator only. |
| `POST /api/reply-drafts/{id}/reject` | Reject a draft awaiting review. Administrator only. |

An AI analysis returns intent, extracted requirement, optional budget and timeline, summary, next action, priority recommendation, and uncertainty notes. The persisted recommendation is separate from the lead's staff-managed priority.

For the enquiry above, a representative mock response is:

```json
{
  "id": 12,
  "leadId": 41,
  "intent": "HIGH",
  "requirement": "3BHK apartment in Greater Noida",
  "budget": "90 lakh",
  "timeline": "within two months",
  "summary": "The customer mentioned requirement: 3BHK apartment in Greater Noida, budget: 90 lakh, timeline: within two months. The enquiry mentions a visit or viewing.",
  "nextAction": "Confirm the customer’s preferences and ask for suitable times for a visit.",
  "recommendedPriority": "HIGH",
  "uncertaintyNotes": "The message contains a concrete visit or viewing signal.",
  "createdAt": "2026-11-18T10:03:00Z",
  "provider": "mock"
}
```

Draft workflow values are `DRAFT`, `PENDING_REVIEW`, `APPROVED` and `REJECTED`. A staff member with record access can edit a draft and submit it for review. Administrators can approve or reject a pending draft. A rejected draft can be reopened for editing. An approved draft is immutable.

A submit-for-review PATCH can include the updated text:

```json
{
  "body": "Thank you for reaching out. What times would work for a site visit, and is there a preferred neighbourhood?",
  "status": "PENDING_REVIEW"
}
```

## Follow-ups, metrics and health

| Method and path | Purpose |
| --- | --- |
| `POST /api/follow-ups` | Schedule work for a visible lead and an eligible assignee. |
| `GET /api/follow-ups` | View upcoming, overdue or completed work in the current user's scope. |
| `PATCH /api/follow-ups/{id}` | Update a follow-up or mark it completed. |
| `GET /api/dashboard/stats` | Return database-backed lead counts, follow-up counts and conversion metrics. |
| `GET /health` | Check API and database readiness without logging in. |

The follow-up list supports `leadId` and `view=ALL|UPCOMING|OVERDUE|COMPLETED`. Its page envelope uses `items`, `totalElements`, `totalPages`, `page` and `size`. Send `{"completed":true}` to complete an item. Administrators can see all follow-ups. Agents can manage work on their assigned leads or follow-ups directly assigned to them. For directly assigned work on another agent's lead, the row withholds the lead's name and returns `canOpenLead=false`.

Example follow-up creation body:

```json
{
  "leadId": 41,
  "assigneeId": 7,
  "note": "Confirm two possible times for a site visit.",
  "dueAt": "2026-12-01T09:30:00Z"
}
```

Use an eligible salesperson ID. If `assigneeId` is omitted, the service uses the lead's current agent or the creating agent when applicable. An administrator scheduling work for an unassigned lead must supply the assignee.

The dashboard returns `totalLeads`, `newLeads`, `qualifiedLeads`, `wonLeads`, `lostLeads`, `highPriorityLeads`, `overdueFollowUps`, `leadsBySource`, `leadsByStatus` and `conversionRate`. Conversion is `100 × wonLeads / totalLeads` rounded to two decimal places, with zero for an empty set. `GET /health` returns `{"status":"UP"}` on success or `{"status":"DOWN"}` with `503` when the database cannot be reached.

## Responses and errors

A successful read returns `200`. Resource creation uses `201`. Logout and lead deletion use `204`. Malformed input returns `400`. Missing authentication returns `401`, and access denied by an authenticated role or CSRF check returns `403`. A missing or out-of-scope record can return `404`. A duplicate enquiry or invalid review transition returns `409`. Rate-limited requests return `429` with `Retry-After`. AI failures return `502` for a provider error or `504` for a timeout. The existing lead remains intact.

Errors use `application/problem+json`. Validation errors can include a field-level map. Example for a missing required customer name:

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Check the highlighted fields.",
  "instance": "/api/leads",
  "fieldErrors": {
    "customerName": "must not be blank"
  }
}
```

Once finished, log out and remove the temporary cookie jar:

```bash
curl -fsS -b "$jar" -H "$header: $token" -X POST "$base/api/auth/logout"
rm -f "$jar"
```
